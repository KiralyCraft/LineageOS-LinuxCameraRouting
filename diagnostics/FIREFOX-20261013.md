# Firefox reconfiguration failure, 2026-10-13

## Reproduced on the installed stack

APK 0.1.5, Magisk module 0.1.3, source d8bf623. Firefox 154.0, build
20260818231248, SourceStamp 9ce1ee6baeb9a3c326dbd180bdece65d8fc2eadc.
The user reported front-camera failure and rear capture freezing when
webcamtests.com moved from initial 640x480 to its maximum-resolution test.
Old helper logcat had rotated away; CameraService retained three rear-camera
connections from that morning and no front-camera connection. This does not
identify the exact original front-camera failure.

Reproduction used a separate headless Firefox profile in RAM-backed /tmp,
Marionette and a localhost-only test page. No user browser was closed or changed,
and no camera frame was sent to a website. Permission bypass applied only to
this disposable profile. Capture was real V4L2, not Firefox fake media.

Both front and main rear captured at 640x480@30. Applying exact 1920x1080
constraints then failed with OverconstrainedError. The track stayed live, but
no new camera capture was established. A second run with ioctl tracing confirmed:

1. VIDIOC_STREAMOFF returns success on the old camera handle.
2. Firefox opens the same camera and sends S_FMT for 1920x1080: EBUSY.
3. Firefox attempts to restore 640x480: also EBUSY.

See `firefox-reconfigure-20261013.txt` for the filtered actual ioctl records.
Firefox's CamerasParent log reports failure both to update the capture and to
restore its previous capability. Front and rear show the same pattern. Front
standalone capture succeeds, so a separate intrinsic front-camera failure is
not established. An immediate device-switch test also opened the front camera;
the original site's exact front-selection failure still needs post-fix retest.

Headless getVideoPlaybackQuality returned zero frame counts for these streams;
that counter was not used as evidence of delivery. Successful DQBUF calls with
advancing sequence/timestamps and native producer completion logs establish
capture. Advancing video currentTime alone is not a freshness test.

## Cause and implementation

The old stop path notified the Android helper and returned immediately while
`stopping` remained true. S_FMT and STREAMON deliberately reject that state to
prevent reuse before Camera2/reader/exported mappings are retired. Firefox's
normal immediate stop/reopen sequence therefore raced the producer shutdown.
The correct safety gate exposed an incomplete consumer stop contract.

The new kernel file-operation wrappers finish STREAMOFF/final close by waiting
for the actual existing CAMERA_ACK_STOP. They run after video_ioctl2 or
vb2_fop_release has dropped the queue mutex; waiting inside stop_streaming
would deadlock the producer's QUERY/ACK ioctls. V4L2 retains the open device
reference until the wrapper returns. A per-camera wait queue wakes after
admission release on valid acknowledgment, or on producer disconnect.

No sleeps, frame pacing, additional frame copy, or producer-protocol change.
A five-second fault deadline bounds a stuck helper; timeout and interruption
leave retirement blocked and never imply that the buffers are safe to reuse.
Generic busy checks, generation/token checks, and fast packing remain intact.

The synthetic lifecycle test now runs consumer retirement concurrently with its
producer and checks that STREAMOFF/close stay pending before ACK, complete after
ACK, support immediate restart/reformat, reject stale writes and early restart,
retain retirement after signal interruption and timeout, and wake on producer death. These kernel-dependent checks require the candidate
module; building the test is not a live pass.

## Deployment and qualification boundary

0.1.6 is a module fix candidate. The existing 0.1.5 APK can acknowledge retirement
already and is compatible. No APK update is required. Package the module, let the
user install it manually and reboot, then enable Linux cameras and rerun the
browser resize/device-switch and synthetic lifecycle tests. The running module
was not replaced during this investigation. Images/logs stay in RAM; only
filtered ioctl evidence and this report are committed.

## Candidate build and retained regression

Exact-kernel LTO/CFI module, Android userspace/APK, and the expanded lifecycle
binary build successfully on the designated build server. Both packing sanitizer
suites pass, including 224 guarded equivalence cases. The new kernel lifecycle
tests have not been executed against 0.1.6 yet.

`python tests/firefox_reconfigure.py` creates a fresh headless profile and
localhost test page, traces real V4L2 ioctls in RAM, and checks front/rear
640x480-to-1080p changes. It was run against the installed module and correctly
failed on the front-camera reconfiguration with OverconstrainedError. Browser
cleanup completed; no camera clients remained. Re-run after manual module
installation; confirm advancing DQBUF sequence/timestamps after each restart
as well as the reported settings.
